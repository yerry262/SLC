# Migration Plan: SLC-DASHBOARD-2024 → SLC

## Why

`SLC-DASHBOARD-2024` (`~/CLAUDE_CORNER/SLC-DASHBOARD-2024`) is the original
dashboard: a set of Jupyter notebooks run through Voila + ngrok, reading live
from beaconcha.in's website/API and a local Ethereum node's Web3 RPC. `SLC`
(this repo) is its from-scratch replacement: React/TS/Vite frontend, static
JSON snapshots generated by Python fetch scripts, deployed to GitHub Pages —
no live backend, no notebook server, no ngrok tunnel. This document maps every
notebook/module in the old repo to where its logic should land here, what's
already done, what's still open, and what should deliberately NOT be ported
as-is.

This is a planning document, not a changelog — update it as migration steps
actually happen (check items off, add dates) rather than treating it as
finished once written.

## Read this first: things in the old repo that must NOT be copied verbatim

1. **Hardcoded API keys, committed to git history:**
   - `SLC/Funct.py:15` — a live CoinMarketCap API key
     (`X-CMC_PRO_API_KEY`) hardcoded in `get_eth_price()`.
   - `SLC/NODE.py:1` — a live Infura project URL/key
     (`mainnet.infura.io/v3/<key>`) as the default `provider_url`.
   - **Action before/independent of migration:** treat both keys as
     compromised (they're sitting in a git history yerry controls, but still)
     and consider rotating them. Neither should be re-hardcoded here — SLC's
     existing `scripts/fetch_*.py` convention (`os.environ.get(...)`, see
     `fetch_fleet.py:39-40`) is correct and should be followed for anything
     new: ETH/USD price fetch, any future Infura/Alchemy fallback, etc.
   - SLC no longer needs Infura at all for chain reads — Phase 1 architecture
     reads the home node directly over `ethereum-wg` (see this repo's
     `CLAUDE.md`). Infura would only re-enter the picture as a redundant
     public fallback, and if so, via an env var/GitHub secret, never a
     literal URL.

2. **Real per-investor financial data, committed to git:**
   - `SLC/InvestmentData_from_excel.py` (generated from a private Google
     Sheet — see `INTERNAL_investor_update_table.ipynb`) contains real dollar
     amounts, per-investor ETH allocations, and a paid-out transaction hash,
     keyed to specific wallet addresses via `Varibles.py`'s `wallet_alias`.
   - This is **out of scope for SLC as currently defined**: this repo's
     `CLAUDE.md` describes a dashboard for "yerry's home-run validators" —
     single-operator earnings/performance, not a multi-investor pool ledger.
     Porting investor-pool accounting is a materially bigger feature (new
     data model, likely needs auth/access control since it's per-person
     financial data) and should be a deliberate, explicit decision — not
     something that rides along with a "port the backend" pass.
   - **If** it's ever decided this belongs in SLC: it must not land as a
     committed JSON file the way `fleet.json`/`earnings.json` do today,
     because this repo's `CLAUDE.md` "Known Limitations" already flags that
     GitHub Pages built from a private repo may still be publicly reachable.
     Real investor dollar figures are a different sensitivity class than
     yerry's own validator balances.

3. **Visitor analytics / access logs:**
   - `INTERNAL_who_is_connecting.ipynb` parses nginx/Voila access logs and
     geolocates visitor IPs to lat/lon, plotted on a US map.
   - Not portable even in principle: SLC is a static site with no server, so
     there are no access logs to parse. It also captured real visitor
     IP→location data (family/investors who'd loaded the old dashboard) —
     don't recreate an equivalent by wiring up e.g. GitHub Pages analytics
     without a separate, explicit conversation about it.
   - `version.py`'s `easteregg` flag is what wired this notebook into
     `Validator_online.ipynb` in the old dashboard (a hidden checkbox).
     That coupling shouldn't be recreated.

## Gaps summary (things with no current home in SLC)

1. **Tip-jar liquid wallet balances** (`Validator_Wallets.ipynb`) — real
   accumulated tip balance per validator's fee-recipient wallet, plus the
   "ETH until next validator" countdown. Straightforward: it's a handful of
   `eth_getBalance` calls against the node's Geth RPC, same pattern
   `fetch_fleet.py` already uses for other data.
2. **Historical/lifetime block-proposal data** (`Validator_Staking_Blocks.ipynb`)
   — blocked on the same Prysm slashing-protection DB export (or beaconcha.in
   Phase 2) already called out in `earnings.json`'s own notes. Not a new
   blocker, just not yet actioned.
3. **APR / ROI% metrics and CL-reward figures** (`Validator_Earnings.ipynb`) —
   blocked on beaconcha.in Phase 2 (HTML scraping is confirmed dead) or a
   from-chain computation of consensus-layer rewards analogous to what
   `fetch_earnings.py` already does for EL tips.
4. **ETH→USD conversion anywhere in the UI** — `Funct.py`'s `get_eth_price()`
   has no equivalent in SLC yet; every figure today is ETH-only.
5. **Static "About/Mission" content** (`Validator_Mission.ipynb`) — no data
   gap, just not yet written into the new frontend. Cheapest item on this list.
6. **Charting library decision** — the old dashboard used Plotly + matplotlib
   (interactive block charts, investor allocation charts, relay pie chart,
   US visitor map). SLC's `frontend/package.json` has no charting dependency
   yet. Needed before porting `Validator_Staking_Blocks.ipynb`'s interactive
   chart or any investor chart (if that scope is ever approved).

## Suggested migration order

Roughly cheapest/lowest-risk → most involved, and independent of each other
(no item below blocks another):

1. **About/Mission static content** — no data dependency, pure copy + layout.
2. **Tip-jar liquid wallet balances** — new `scripts/fetch_wallets.py` +
   `frontend/src/data/wallets.json` + a small panel, following the exact
   pattern of `fetch_fleet.py`/`fetch_earnings.py` (env-var secrets, retry
   wrapper, node-direct reads over `ethereum-wg`). Include the "ETH until
   next validator" countdown as a derived value, not a stored one.
3. **ETH→USD conversion** — add a price fetch (CoinGecko's public API is a
   reasonable no-key default; CoinMarketCap needs its own fresh key via env
   var if preferred) and thread `eth_price` through the existing panels as an
   optional secondary figure, matching `Funct.py`'s `eth_to_usd`/`format_with_commas`
   intent without copying its hardcoded key.
4. **Charting library pick** — small spike/decision needed (e.g. Recharts,
   visx, or lightweight Plotly.js) before item 5 or 6 can proceed.
5. **APR/ROI/CL-reward metrics** — depends on beaconcha.in Phase 2 (this
   repo's `CLAUDE.md` already tracks that as an open item) or a chain-native
   CL-reward computation.
6. **Historical block-proposal data** — depends on the Prysm DB export
   decision (stopping the live validator briefly) or beaconcha.in Phase 2.
7. **Investor-pool accounting** — explicitly deferred; needs its own
   go/no-go conversation given the sensitivity of real per-person financial
   data and this repo's public-reachability caveat, before any design work
   starts.

## Where to look for how-tos

- **Fetch-script conventions** (env-var secrets, retry-wrapped HTTP, node IP
  constants): `scripts/fetch_fleet.py` — read this first, it's the reference
  implementation the others (`fetch_earnings.py`, `fetch_performance.py`)
  already follow.
- **Data-shape conventions**: each `frontend/src/data/*.json` file pairs with
  a TypeScript interface in `frontend/src/types.ts` — follow that pairing for
  any new data file.
- **Node access details** (IPs, ports, WireGuard alias): this repo's
  `CLAUDE.md` under "Ethereum node box" reference, and
  `~/CLAUDE_CORNER/CLAUDE.md`'s own "Ethereum node box" section.
- **Old repo's raw source of truth**, if a number here needs re-checking
  against the original: `~/CLAUDE_CORNER/SLC-DASHBOARD-2024/SLC/` — treat it
  as read-only reference during migration, not something to edit.
